# 효과 안의 setState 때문에 프론트엔드 CI lint 가 막힘

- 상태: **해결** (2026-09-04)
- 최초 작성: 2026-09-04
- 관련 파일: `frontend/src/features/folders/FolderListPage.tsx`
- 관련 PR: #32
- 관련 커밋: `abc5123`

---

## 문제

PR #32 의 CI 가 프론트엔드 job 에서 멈췄다. `npm ci` 는 지나갔고 `npm run lint` 에서 죽었다.

```
/frontend/src/features/folders/FolderListPage.tsx
  68:5  error  Calling setState synchronously within an effect can trigger cascading renders

  67 |   useEffect(() => {
> 68 |     setIsDeleteMode(false)
     |     ^^^^^^^^^^^^^^^ Avoid calling setState() directly within an effect
  69 |     setSelectedTaskIds(new Set())
  70 |     setDeleteError(null)
  71 |     setTaskFilter(EMPTY_TASK_FILTER)  react-hooks/set-state-in-effect

✖ 1 problem (1 error, 0 warnings)
```

문제의 코드는 폴더 화면과 할 일 화면을 오갈 때 삭제 선택과 필터를 초기화한다.

```tsx
useEffect(() => {
  setIsDeleteMode(false)
  setSelectedTaskIds(new Set())
  setDeleteError(null)
  setTaskFilter(EMPTY_TASK_FILTER)
}, [activeView])
```

---

## 원인

`eslint-plugin-react-hooks` 가 7.1.1 이다. 7 버전부터 React Compiler 의 진단이 룰로 들어왔고
`react-hooks/set-state-in-effect` 도 그중 하나다. 설정은 `reactHooks.configs.flat.recommended`
를 그대로 쓰고 있어 이 룰이 error 로 켜져 있다.

룰이 지적하는 것은 문법이 아니라 렌더 순서다. React 의 렌더링은 두 국면으로 나뉜다. 컴포넌트
함수를 실행해 무엇을 그릴지 계산하는 **렌더 단계**, 그 결과를 실제 DOM 에 반영하는 **커밋
단계**. `useEffect` 는 커밋이 끝난 뒤에 실행된다.

그래서 효과 안에서 초기화하면 순서가 이렇게 된다.

```
view 바뀜 → 렌더(옛 필터 그대로) → DOM 반영 → 브라우저가 화면에 그림
         → 효과 실행 → setState 4 개 → 다시 렌더 → 다시 DOM 반영
```

초기화되기 전 상태가 한 프레임 화면에 실제로 나타난다. 할 일 화면으로 넘어갈 때 이전 필터가
걸린 목록이 잠깐 보였다 사라진다. 렌더도 두 번 하고 자식 컴포넌트까지 두 번 그린다. 룰이
"cascading renders" 라 부르는 것이 이 왕복이다.

이 효과는 전부터 있었다. 이번에 처음 걸린 것은 CI 가 프론트엔드 job 까지 도달한 것이 최근이기
때문이다. 앞선 실행들은 배포 파이프라인 쪽에서 먼저 죽어 여기까지 오지 못했다.

---

## 대안

| 안 | 방법 | 판단 |
| --- | --- | --- |
| A | 룰을 끄거나 `eslint-disable` 주석 | 증상만 가린다. 깜빡임과 이중 렌더는 그대로 남는다 |
| B | 효과를 지우고 `changeView` 에서만 초기화 | 동작이 바뀐다. 뒤로 가기처럼 URL 로 화면이 바뀌면 초기화되지 않는다 |
| C | 할 일 화면을 컴포넌트로 떼고 `key={activeView}` | React 가 권하는 정공법. 다만 컴포넌트 구조를 바꾸는 리팩터링이다 |
| D | 렌더 중에 이전 값과 비교해 조정 | 동작을 그대로 두고 고칠 수 있다 |

B 를 버린 이유는 `changeView` 가 화면을 바꾸는 유일한 경로가 아니어서다. `activeView` 는
`searchParams` 에서 나오므로 브라우저 뒤로 가기나 링크로도 바뀐다. 효과는 그 경로까지 덮고
있었다.

C 가 가장 React 다운 답이다. state 를 통째로 버리고 싶을 때 `key` 를 주는 것이 문서가 첫
번째로 드는 방법이다. 다만 지금은 CI 가 막혀 있고, 구조를 바꾸면 리뷰 범위가 커진다. 초기화
대상도 전체가 아니라 네 개뿐이다.

D 를 골랐다. 일부 state 만 되돌리는 경우에 문서가 드는 방법이고, 동작이 바뀌지 않는다.

---

## 해결

이전 view 를 상태로 들고 렌더 중에 비교해 맞춘다.

```tsx
const [renderedView, setRenderedView] = useState(activeView)
if (renderedView !== activeView) {
  setRenderedView(activeView)
  setIsDeleteMode(false)
  setSelectedTaskIds(new Set())
  setDeleteError(null)
  setTaskFilter(EMPTY_TASK_FILTER)
}
```

React 는 렌더 도중 그 컴포넌트 자신의 state 가 바뀌면 계산하던 결과를 버리고 그 자리에서
컴포넌트를 다시 실행한다. DOM 에 닿기 전이라 깜빡임이 없고 자식도 다시 그리지 않는다.

```
view 바뀜 → 렌더 시작 → 조건 불일치 → setState → 결과 버리고 즉시 다시 렌더
         → DOM 반영 → 화면에 그림 (초기화된 상태로 한 번만)
```

이 방식에는 조건이 셋 붙는다.

- **반드시 조건부여야 한다.** `if` 없이 부르면 렌더와 setState 가 서로를 불러 무한 루프가 된다.
  조건이 곧 종료 보장이다.
- **자기 자신의 state 만** 바꿀 수 있다. 렌더 중에 다른 컴포넌트의 setState 를 부르면 React 가
  경고한다.
- **부수 효과는 안 된다.** 요청이나 DOM 조작은 효과의 몫이다.

`renderedView` 라는 state 를 하나 더 둔 이유가 여기 있다. 직전 렌더에서 본 값을 기억해야
지금 값과 비교할 수 있고, 비교할 것이 있어야 조건이 성립한다.

같은 파일의 다른 효과(`loadAllTasks`)는 그대로 뒀다. 서버에서 데이터를 받아오는 일이라
효과가 맞는 자리다.

검증은 CI 와 같은 명령으로 했다. `npm run lint` 와 `npm run build`(`tsc -b && vite build`) 모두
exit 0. 커밋 `abc5123` 을 올린 CI run 9 가 통과했다.

---

## 배운 것

- 효과는 "렌더 뒤에 하는 일"이다. 화면에 무엇을 그릴지 정하는 일을 효과에 두면 한 박자 늦는다.
  늦은 만큼 사용자는 옛 화면을 본다.
- 초기화 범위가 판단을 가른다. 전부 버릴 것이면 `key`, 일부만 되돌릴 것이면 렌더 중 조정이다.
- 룰이 오래된 코드를 이제야 잡았다면, 룰이 늦은 것이 아니라 그 코드까지 검사가 닿은 것이 처음인
  경우가 있다. 파이프라인 앞쪽이 막혀 있으면 뒤쪽 검사는 존재하지 않는 것과 같다.
