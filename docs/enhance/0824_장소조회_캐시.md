# Public Places API Cache Design

## Goal

`GET /api/public/places`는 로그인 여부와 관계없이 모든 사용자에게 동일한 장소 목록을 반환한다.

장소 데이터는 시스템이 관리하는 비교적 정적인 데이터이며, 각 장소의 메타데이터와 배경 영상 URL을 포함한다.

애플리케이션 서버까지 들어오는 반복 조회 요청을 줄이기 위해 CloudFront에서 API JSON 응답을 캐시한다.

---

## Request Flow

```text
Client
  │
  │ GET /api/public/places
  ▼
CloudFront
  │
  ├─ Cache HIT
  │    └─ JSON 응답 반환
  │
  └─ Cache MISS
       ▼
     Nginx
       ▼
   Spring Boot
       ▼
     MySQL
````

CloudFront Cache HIT 시 요청은 EC2까지 전달되지 않는다.

---

## API Response

`GET /api/public/places`

* 인증 불필요
* 사용자별 응답 차이 없음
* 장소 메타데이터 및 공개 CDN Asset URL 반환
* 사용자별 상태는 포함하지 않는다.

예:

```json
[
  {
    "id": 1,
    "name": "New York Cafe",
    "backgroundAssetUrl": "https://cdn.example.com/places/1/background-v1.mp4",
    "posterAssetUrl": "https://cdn.example.com/places/1/poster-v1.webp"
  }
]
```

다음과 같은 사용자별 데이터는 해당 API에 포함하지 않는다.

* favorite
* recentlyUsed
* personalized recommendation
* 사용자별 접근 권한

필요한 경우 별도 인증 API로 분리한다.

---

## Cache Policy

### Places API

```http
Cache-Control: public, max-age=300, s-maxage=3600
```

* Browser cache: 최대 5분
* CloudFront cache: 최대 1시간
* 장소 설정 변경 시 CloudFront invalidation 가능

### Video / Image Assets

```http
Cache-Control: public, max-age=31536000, immutable
```

Asset은 동일 Key를 덮어쓰지 않는다.

```text
places/1/background-v1.mp4
places/1/background-v2.mp4
```

새로운 파일 업로드 후 API가 참조하는 Asset Key를 변경한다.

---

## CloudFront Rules

`/api/public/places`에 대해서만 API 응답 캐시를 활성화한다.

```text
/api/public/places
    → API Origin
    → Cache Enabled

/api/*
    → API Origin
    → Cache Disabled
```

Cache Key에 사용자별 정보를 포함하지 않는다.

* Cookie 전달하지 않음
* Authorization Header 전달하지 않음
* 불필요한 Query String 전달하지 않음

이를 통해 모든 사용자가 동일한 CloudFront Cache Object를 공유한다.

---

## Cache Layers

Places 조회에는 Redis 또는 Local Cache를 추가하지 않는다.

```text
CloudFront HIT
→ CloudFront에서 응답

CloudFront MISS
→ Spring Boot
→ MySQL
```

현재 장소 데이터 규모가 작고 변경 빈도가 낮기 때문에 추가 캐시 계층의 복잡성이 얻는 이점보다 크다고 판단한다.

---

## Decision

* Public Places API의 JSON 응답을 CloudFront에서 캐시한다.
* 사용자별 데이터는 Public API와 분리한다.
* Places API TTL은 CloudFront 기준 1시간으로 시작한다.
* 정적 영상/이미지는 1년 `immutable` 캐시를 사용한다.
* 장소 변경이 즉시 반영되어야 하는 경우 CloudFront invalidation을 수행한다.
* Redis/Local Cache는 현재 범위에서는 사용하지 않는다.

```

핵심 설계는 결국 **`CloudFront → Spring → MySQL`에서, 반복적인 조회를 `CloudFront`에서 끝내도록 만드는 것**이야. 장소 목록처럼 모든 사용자에게 동일한 정적성 높은 데이터에는 꽤 깔끔한 선택이야. 
```
