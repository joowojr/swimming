# CloudFront 에 API 경로 통합

- 상태: **진행 중** — 오리진 인증서 발급 대기 (2-3 참고)
- 최초 작성: 2026-09-03
- 관련 파일: `infra/terraform/cdn.tf`, `infra/architecture.md` §8·§9, `frontend/.env.production`, `backend/.../AuthUseCase.java`

---

## 배경

이 문제는 **전달 계층(delivery layer)을 구성하던 중**에 나왔다. 애플리케이션은 로컬에서
동작하고 있었고, 남은 일은 "브라우저가 어떤 경로로 무엇을 받아 가느냐"를 확정하는 것이었다.
구성 요소는 세 개다.

### CloudFront — 엣지와 뷰어 TLS

정적 프론트엔드(S3)를 전 세계 엣지에서 서빙하고, 사용자와의 HTTPS 를 여기서 종료한다.
S3 는 OAC 로 잠가 CloudFront 만 읽게 한다. 뷰어 인증서는 CloudFront 제약상
**us-east-1 ACM** 이어야 한다.

### Nginx — 오리진 리버스 프록시

EC2 한 대에서 Spring Boot 컨테이너 앞에 선다. 8080 을 인터넷에 노출하지 않고 루프백으로만
프록시하며, WebSocket 업그레이드(`/ws/`)를 통과시키는 역할도 여기가 맡는다.

### HTTPS — 두 구간, 두 인증서

TLS 는 한 번이 아니라 두 번 끊긴다. 이 점이 이후 문제의 전제가 된다.

| 구간 | 인증서 | 발급 |
| --- | --- | --- |
| 사용자 ↔ CloudFront | ACM (us-east-1) | DNS 검증, 무료 |
| CloudFront ↔ Nginx | 오리진 인증서 | Let's Encrypt HTTP-01 (certbot) |

### 미결로 남아 있던 것: API 진입 경로

세 요소 중 프론트 경로만 확정되어 인프라 코드에 들어가 있었다. **API 가 어디로 들어오는지는
결정되지 않은 상태였고**, 문서마다 다른 전제를 담고 있었다.

| 위치 | 내용 |
| --- | --- |
| `deployment-checklist.md:31` | "CloudFront의 `/api/*` origin 라우팅과 캐시 정책을 확정한다" — **미결 항목** |
| `deployment-checklist.md:139` | "`/api/*`를 별도 API 도메인으로 분리하거나 CloudFront custom origin으로 라우팅" — **두 안 병기** |
| `infra/architecture.md` §11 (당시) | `api.example.com` → Nginx EIP 로 **분리 전제** |
| `infra/terraform/cdn.tf` | S3 프론트 오리진만 존재 |

즉 "분리로 설계되어 있었다"기보다, **분리와 통합 사이에서 결정이 미뤄진 채 프론트 쪽만
먼저 구현된 상태**였다.

### 문제가 드러난 계기

"CORS 설정을 애플리케이션에 안 해도 되느냐"는 질문이 정확히 그 미결 지점을 건드렸다.
CORS 가 필요한지 여부 자체가 API 진입 경로에 달려 있기 때문이다.

확인해 보니 **CORS 는 이미 구현되어 있었다.**

| 위치 | 내용 |
| --- | --- |
| `common/config/CorsProperties.java` | `app.cors.allowed-origins` 바인딩 |
| `common/config/WebConfig.java` | `/api/**` 에 `allowCredentials(true)` |
| `application-prod.yml:23` | `allowed-origins: ${ALLOWED_ORIGINS}` |

값만 채우면 되는 상태였다. 그런데 분리 전제로 진행할 경우 **CORS 를 올바르게 설정해도
동작하지 않는 문제**가 두 개 더 있다는 것이 함께 드러났다. 미뤄 둔 결정을 지금 내려야
하는 상황이 된 것이다.

## 원인

### 1. 프론트의 API 주소가 상대경로였다

```
frontend/.env.production
API_BASE_URL=/api
```

로컬에서는 Vite dev server 의 프록시가 `/api` 를 `localhost:8080` 으로 넘겨 주므로 문제가
없다. 그러나 프로덕션에서 `/api` 는 **CloudFront 로 간다.** CloudFront 에는 `/api` 오리진이
없으므로 SPA 폴백(`403/404 → /index.html`)이 걸려 **모든 API 호출이 HTML 을 200 으로**
받게 된다.

`vite.config.ts` 에 `envPrefix: ['API_', 'VITE_']` 가 있어 변수 이름 자체는 정상 노출된다.
값이 잘못된 것이지 설정이 빠진 것이 아니다.

### 2. 리프레시 쿠키가 `SameSite=Lax` 였다

```java
// auth/usecase/AuthUseCase.java:104
.sameSite("Lax")
```

`Lax` 쿠키는 **크로스사이트 XHR 에 실려 나가지 않는다.** 분리 구조에서 프론트와 API 가
브라우저 기준 서로 다른 사이트라면, 로그인은 되는데 **토큰 갱신이 조용히 실패**하는
형태로 나타난다. 원인 파악이 어려운 종류의 버그다.

> **정정 (2026-09-03)**: 당시에는 `kro.kr` 이 무료 서브도메인 서비스이므로 Public Suffix
> List 에 등재되어 있을 것이라 판단했고, 그래서 두 호스트가 다른 사이트라고 봤다. 이후
> Let's Encrypt 가 등록 도메인을 `kro.kr` 로 판정하는 것을 확인해(아래 3차 문제 참고)
> **PSL 에 없다**는 사실이 드러났다. 즉 두 호스트는 같은 사이트이고, 분리 구조에서도
> `SameSite=Lax` 는 동작했을 것이다. 이 근거는 무효다. 통합 결정은 나머지 근거
> (배포 형상과 애플리케이션 코드의 결합 제거, WAF 자리 확보) 위에서 유지한다.

### 공통 뿌리

두 문제 모두 개별 버그가 아니라 **"프론트와 API 가 서로 다른 오리진"** 이라는 배포 형상
하나에서 파생됐다. 그래서 개별 수정보다 형상 자체를 다시 볼 필요가 있었다.

## 대안

| | A. 분리 유지 | B. CloudFront 에 통합 |
| --- | --- | --- |
| 변경 범위 | 애플리케이션 코드 2곳 | 인프라(`cdn.tf`) |
| CORS | `ALLOWED_ORIGINS` 값 설정 | **불필요** (동일 오리진) |
| SameSite | `None` 으로 변경 필요 | `Lax` 그대로 유효 |
| 프론트 API 주소 | 절대 URL 로 변경 필요 | `/api` 상대경로 그대로 유효 |
| WAF | API 앞에 붙일 자리 없음 | CloudFront 에 붙이면 API 까지 커버 |
| API 노출 | EIP 로 직접 노출 | CloudFront 뒤로 (우회 접근은 별도 차단 필요) |
| 위험 | 없음 | **캐시 정책 오설정 시 인증 정보 유출** |
| 추가 비용 | 없음 | AWS 리소스 증가 없음 (배포 내부 블록) |

### 선택: B

이유는 세 가지다.

1. **애플리케이션 코드를 배포 형상에 맞춰 바꾸지 않아도 된다.** A 를 택하면 `SameSite` 와
   API 주소가 "이 인프라라서 이렇게 되어 있다"는 암묵적 결합이 된다.
2. WAF 를 붙일 자리가 생긴다.
3. API 도 엣지에서 TLS 를 종료하게 된다.

B 의 위험(캐시 오설정)은 정책을 명시적으로 고정하는 것으로 통제 가능하다고 판단했다.

## 해결

### 구현

`infra/terraform/cdn.tf` 의 **기존 배포 안에** 블록 두 개를 추가했다. 새 AWS 리소스는
늘지 않는다.

```hcl
dynamic "origin" {                       # api_domain_name 이 null 이면 생성되지 않음
  content {
    origin_id   = "api"
    domain_name = origin.value
    custom_origin_config {
      origin_protocol_policy = "https-only"
      origin_ssl_protocols   = ["TLSv1.2"]
    }
  }
}

dynamic "ordered_cache_behavior" {
  content {
    path_pattern             = "/api/*"
    target_origin_id         = "api"
    viewer_protocol_policy   = "https-only"
    allowed_methods          = ["GET","HEAD","OPTIONS","PUT","POST","PATCH","DELETE"]
    cache_policy_id          = data.aws_cloudfront_cache_policy.caching_disabled.id
    origin_request_policy_id = data.aws_cloudfront_origin_request_policy.all_viewer.id
  }
}
```

각 선택의 근거:

| 설정 | 이유 |
| --- | --- |
| `Managed-CachingDisabled` | 캐싱 정책은 `Authorization`·`Cookie` 를 **오리진에 전달하지 않고** 응답을 캐싱한다. API 에 적용하면 한 사용자의 응답이 다른 사용자에게 나간다. |
| `Managed-AllViewer` | 헤더·쿠키·쿼리스트링을 그대로 전달한다. 없으면 JWT 와 리프레시 쿠키가 백엔드에 도달하지 않는다. |
| 뷰어 `https-only` | `redirect-to-https` 는 HTTP POST 에 301 을 돌려주어 **요청 본문을 잃는다.** |
| 오리진 `https-only` | CloudFront ↔ EC2 구간이 공개 인터넷을 지나므로 평문 금지. 대신 오리진 인증서가 필요해진다. |
| 메서드 확장 | 기본 비헤이비어는 `GET/HEAD/OPTIONS` 뿐이라 POST 가 막힌다. |

### 통합하면서 드러난 2차 문제

#### 2-1. `custom_error_response` 는 배포 전역이다

기존 SPA 폴백이 이렇게 되어 있었다.

```hcl
custom_error_response { error_code = 403  response_code = 200  response_page_path = "/index.html" }
custom_error_response { error_code = 404  response_code = 200  response_page_path = "/index.html" }
```

`custom_error_response` 는 **배포 전체에 적용되며 비헤이비어별로 분리할 수 없다.** 이 상태로
API 를 붙이면 백엔드의 404·403 ProblemDetail 응답까지 HTML + 200 으로 바뀌어 API 가
망가진다.

**해결**: 두 블록을 제거하고 CloudFront Function 을 **기본 비헤이비어에만** 붙였다.

```js
function handler(event) {
  var request = event.request;
  // 확장자가 없는 경로 = React Router 경로
  if (request.uri.indexOf('.') === -1) {
    request.uri = '/index.html';
  }
  return request;
}
```

`/api/*` 는 별도 비헤이비어이므로 이 함수를 거치지 않는다.
부수 효과로 **실제로 없는 정적 파일이 index.html 로 가려지지 않고** 자기 상태 코드를
그대로 돌려주게 됐다. 이전보다 나은 동작이다.

#### 2-2. CloudFront 커스텀 오리진은 IP 를 받지 않는다

오리진은 도메인 이름만 지정할 수 있고, `https-only` 라 CloudFront 가 오리진 인증서를
검증한다. 즉 **통합해도 API 호스트명과 certbot 은 없어지지 않는다.**

**해결**: 기존 이름 아래 하위 도메인을 하나 둔다. 새 호스트명을 발급받을 필요는 없다.

| 호스트명 | 레코드 | 대상 | 용도 |
| --- | --- | --- | --- |
| `swimming-now.kro.kr` | CNAME | CloudFront | 사용자가 보는 주소 |
| `api.swimming-now.kro.kr` | **A** | `3.37.218.161` (EIP) | CloudFront `/api/*` 오리진 |
| `_xxxx.swimming-now.kro.kr` | CNAME | ACM 검증값 | 인증서 발급·갱신 |

CNAME 으로는 IP 를 가리킬 수 없으므로 오리진용 레코드는 반드시 **A** 여야 한다.
이 이름은 CloudFront ↔ EC2 사이에서만 쓰이고 사용자에게 노출되지 않는다.

#### 2-3. Let's Encrypt 쿼터를 `kro.kr` 사용자 전원이 공유한다

2-2 에서 필요해진 오리진 인증서를 발급하려다 막혔다.

```
too many certificates (50) already issued for "kro.kr" in the last 168h0m0s,
retry after 2026-09-03 06:55:12 UTC
```

주목할 곳은 한도 수치가 아니라 **판정된 등록 도메인이 `api.swimming-now.kro.kr` 이 아니라
`kro.kr` 이라는 점**이다. Let's Encrypt 는 Public Suffix List 로 등록 도메인을 정한다.
`kro.kr` 이 PSL 에 있었다면 `swimming-now.kro.kr` 이 등록 도메인이 되어 우리만의 쿼터를
가졌을 것이다. 그렇지 않다는 것은 **`kro.kr` 을 쓰는 모든 사용자가 주당 50 장이라는 하나의
쿼터를 나눠 쓴다**는 뜻이다. 우리 도메인과 무관하게 남들이 소진한 것이고, **우리가 통제할
수 있는 변수가 아니다.**

이 사실은 원인 §2 의 SameSite 판단을 뒤집는 근거이기도 하다. 해당 절의 정정 참고.

**완화 요인**: 에러가 가리키는 문서 앵커가 `#new-certificates-per-registered-domain` 이다.
**신규 발급**에만 걸리는 한도이고 동일 도메인 갱신은 제외된다. 즉 최초 1 회만 통과하면
이후 60 일 주기의 갱신은 이 경합을 다시 겪지 않는다. 문제는 첫 발급 한 번이다.

**대안**

| 방안 | 비용 | 확실성 |
| --- | --- | --- |
| A. 창이 열린 뒤 재시도 | 0 | 복권. 다른 사용자가 계속 소모하므로 실패할 수 있다 |
| B. 다른 ACME CA (Buypass Go SSL) | 0 | `kro.kr` 공유 쿼터와 무관. `--server https://api.buypass.com/acme/directory` |
| C. 도메인 구입 | 연 1~2 만원 | 근본 해결. 공유 쿼터도 PSL 문제도 사라진다 |
| D. ALB + ACM 오리진 인증서 | 월 약 $18 | Let's Encrypt 자체가 불필요해진다. 헬스체크·무중단 배포 기반도 생긴다 |

**선택**: A 를 먼저 시도하고 실패하면 B 로 간다. C 는 중기 과제로 둔다. kro.kr 은 이 쿼터
문제 외에도 무료 서브도메인 서비스라는 제약을 계속 안고 가기 때문이다. D 는 현재 규모에
과하다.

**실행 시 주의**: `--dry-run` 은 스테이징 서버를 쓰므로 쿼터를 소모하지 않는다. 실제 발급
전에 DNS·nginx·ACME 경로를 이것으로 먼저 검증한다. 발급 실패를 반복하는 것이 가장 비싼
선택이다.

### 순서 제약

`enable-tls` 로 오리진 인증서를 발급하기 전에는 `/api/*` 가 **502** 를 반환한다.
CloudFront 가 오리진 인증서를 검증하기 때문이다. 인증서가 생기면 추가 apply 없이 붙는다.

```
1. api.swimming-now.kro.kr  A → 3.37.218.161 등록
2. terraform apply
3. sudo /opt/swimming/bin/enable-tls api.swimming-now.kro.kr <이메일>
```

## 결과

통합의 직접적 효과로 **원인 1·2 가 코드 수정 없이 해소**됐다.

| 항목 | 조치 |
| --- | --- |
| `frontend/.env.production` 의 `API_BASE_URL=/api` | **수정 불필요.** 동일 오리진이므로 상대경로가 올바르다 |
| `AuthUseCase.java` 의 `sameSite("Lax")` | **수정 불필요.** 크로스사이트가 아니므로 Lax 로 충분하다 |
| `ALLOWED_ORIGINS` | `@NotEmpty` 검증 때문에 값은 필요하지만, 동일 오리진 요청은 CORS 를 타지 않아 실제로는 사용되지 않는다 |

## 향후 과제

- **WebSocket**: 그룹 세션(슬라이스 8) 구현 시 `/ws/*` 비헤이비어가 필요하다. CloudFront 의
  WebSocket 지원 조건과 유휴 타임아웃을 그때 검증해야 한다.
- **우회 접근 차단**: `api.swimming-now.kro.kr` 로 CloudFront 를 건너뛴 직접 접근이 가능하다.
  app-sg 의 443 인바운드를 CloudFront 관리형 접두사 목록
  (`com.amazonaws.global.cloudfront.origin-facing`) 으로 좁힐 수 있다. 80 은 ACME 갱신
  때문에 열어 두어야 한다.
- **WAF**: 통합으로 붙일 자리가 생겼으나 아직 적용하지 않았다.
